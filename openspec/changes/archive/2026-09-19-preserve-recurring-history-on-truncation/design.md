## Context

Recurring tasks are stored as a series definition plus sparse `TaskOccurrenceState` rows for completed, skipped, or modified occurrences. A truncation changes the time span generated by the series. State anchored after the new boundary can therefore stop overlaying any generated occurrence even though it records an action the user already took.

The calendar read path is recurrence-expansion-heavy, while truncation is rare. Recurring definitions are also consumed by calendar and notification expansion, so a definition that claims to recur without a rule can break work far beyond the write that created it.

## Goals / Non-Goals

**Goals:**

- Preserve completed facts and deliberate occurrence placement across every series-truncation path.
- Give orphaned state an explicit, queryable persistence classification.
- Prevent recurring definitions without a rule at both application and database boundaries.
- Keep notification processing for valid series running when one stored rule cannot be expanded.
- Keep the cut identity distinct from the replacement series' supplied start schedule.

**Non-Goals:**

- Automatically reattach detached state if a later recurrence rule generates its anchor again.
- Add a root identifier spanning successor series.
- Copy comments or subtasks to a successor series.
- Define client-specific visual treatment for detached occurrences.
- Define detached-occurrence mutation semantics; those are covered by the separate `enforce-nonretroactive-recurrence-and-detached-lifecycle` change.

## Decisions

### Store detached classification

`TaskOccurrenceState` stores a non-null `detached` flag. Truncation already identifies the affected rows, so classifying them on the rare write avoids re-expanding historical rules on every day or week query. The accepted trade-off is that detached state is not automatically reattached after a later definition change.

Deriving detachment at read time was rejected because it moves recurrence-history work into the hottest query path. Converting orphaned occurrences into ordinary tasks was rejected because it loses their relationship to the originating series.

### Preserve DONE and MODIFIED, remove SKIPPED

A completed occurrence records an event that happened, and a modified occurrence records a deliberate placement or override. Both remain meaningful outside the current series span and become detached. A skipped row represents only the absence of a generated occurrence; after truncation removes that occurrence, the row has no independent meaning and is deleted.

All truncation and split operations delegate this classification to one occurrence-state operation after persisting the original series boundary.

### Query detached state independently

Detached rows cannot be discovered through the set of series active in the requested period. Calendar queries therefore fetch detached state by its own effective schedule, load the referenced series definitions, and merge the resulting materialized occurrences with normally expanded results. Moved attached state remains bounded by the current series span to avoid displaying stale orphaned rows twice.

### Enforce recurrence integrity at two boundaries

Every application write that produces a recurring definition validates that its recurrence rule is non-null and non-blank. A database `CHECK` constraint provides the same final invariant for paths outside the application. Existing invalid rows are converted to non-recurring tasks and have their recurrence end cleared because, without a rule, they cannot generate a series.

Syntactically malformed non-blank rules remain possible in legacy or externally modified data. Notification candidate expansion catches failures per series, logs the unusable definition, and continues with all other series.

### Keep split boundary and successor schedule separate

The occurrence identity in a `FROM_THIS` operation determines where the original series ends. A supplied replacement `scheduledAt` determines the successor's DTSTART and is therefore retained. The cut instant is used only as the fallback when a partial series update does not supply a new schedule.

## Risks / Trade-offs

- [Detached state can become stale if a later rule covers the same anchor] → The persisted flag is authoritative; automatic reattachment is explicitly deferred.
- [Required `isDetached` can break clients that strictly model occurrence responses] → The OpenAPI and MCP contracts expose the field; client presentation and compatibility work are tracked separately.
- [A malformed non-blank rule can still enter through manual database changes] → Notification expansion isolates that series, while normal application writes and the database prevent missing or blank rules.
- [Successor series receive a new identifier] → Fragmentation is accepted; cross-series root identity and relationship copying remain deferred.

## Migration Plan

1. Convert recurring task rows with a null or blank rule into non-recurring tasks and clear their recurrence end.
2. Add the database recurrence-rule constraint.
3. Add the non-null `detached` column with a false default.
4. Delete orphaned skipped states and mark orphaned completed or modified states detached.
5. Add the detached-state query index.

Rollback must remove the detached-state index, column, and recurrence constraint before rolling application code back. The repaired task classification and deleted orphaned skips are intentionally not reconstructed.

## Open Questions

None for this change. Client rendering, `series_root_id`, and relationship copying remain separate product decisions.
