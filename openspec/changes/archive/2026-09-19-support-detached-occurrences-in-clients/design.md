## Context

The task API now marks recurring-occurrence responses with required `isDetached` state. Angular and Android predate that property, so detached occurrences remain visually indistinguishable from generated occurrences. Both clients also use recurrence-scope controls designed for generated occurrences, even though a detached occurrence has no following generated tail at its stable anchor.

Angular task detail receives the selected occurrence representation directly. Android navigation retains only the series ID and occurrence identity, then reloads `/tasks/{taskId}`, which returns the series definition and loses occurrence state, including detachment and overrides.

## Goals / Non-Goals

**Goals:**

- Make `isDetached` part of both maintained client models.
- Label detached occurrences consistently as `Hors série` in list and detail contexts.
- Route all supported detached mutations directly to their stable occurrence identity without asking for recurrence scope.
- Prevent series-only properties from appearing editable on detached occurrence detail.
- Let Android reload the authoritative occurrence representation after navigation or process restoration.

**Non-Goals:**

- Change how detachment is calculated or persisted.
- Add new override fields to `TaskOccurrenceState`.
- Change recurrence-rule editing or stopping-series behavior for attached occurrences.
- Add automatic reattachment to a later recurrence rule.

## Decisions

### Add a dedicated occurrence read operation

`GET /tasks/{taskId}/occurrences/{occurrenceScheduledAt}` returns one `RecurringTaskOccurrenceDto`. The service resolves existing state first, accepts detached state by persisted identity, and otherwise requires the current rule to generate the requested occurrence. Skipped occurrences and fabricated identities are unavailable.

Using the same resource path as occurrence replacement keeps the identity contract consistent across GET and PUT. Passing a full DTO through Android activity extras was rejected because it becomes stale, complicates serialization, and does not survive all recreation paths as an authoritative server value.

### Treat detached occurrences as occurrence-only resources

The clients use `isDetached` to bypass every scope chooser. Content, priority, schedule, deadline, completion, reopening, and deletion target the occurrence identity directly. Properties unsupported by occurrence state—type, description, project, labels, estimate, and recurrence rule—are presented read-only or hidden from editing while detached.

This avoids implying that `FROM_THIS` exists for an anchor no longer generated by the series and prevents unsupported occurrence payloads.

### Use one cross-client label

Both clients display the literal French label `Hors série` with non-color-only text. It appears in task rows where detached occurrences are listed and in task detail. Styling follows each client's existing compact metadata or chip treatment.

## Risks / Trade-offs

- [The new GET adds another public task operation] → It reuses the existing occurrence identity, result, mapper, validation, and error handling rather than introducing a parallel representation.
- [Detached detail exposes fewer editable properties] → Disabled or hidden controls reflect the fields the occurrence persistence model can actually store.
- [Badge placement varies slightly by platform] → Text and semantics remain identical; layout follows native platform conventions.
- [Attached occurrence behavior could regress while routing is specialized] → Tests cover attached scope dialogs separately from detached direct mutations.

## Open Questions

None. The product decisions are fixed: display `Hors série` and never ask for mutation scope on a detached occurrence.
